# 项目管理：建议与规划（自然语言，不是硬校验）

> **这一篇是"建议"，不是"规则"。** 它讲怎么想、怎么选、什么时候该停下来问人。
> 机器只核对**形式**（卡在不在、真身指不指得到 —— 体检 `cards` 项）；
> **判断类的事**（该不该建项目、要不要外发、算不算退役）**没有脚本能替你决定**，读这一篇，人拍板。

## 〇、先看这 8 行（结论）

1. **一个项目只有一处真身**：代码、测试、产物都在那里，**改动只在那里**。
2. 工作区里只留一张**登记卡**（`projects/<名>/README.md`，默认 ≤40 行，只放指针）。
3. 老版本、事故物证进**回退副本**（一个专门的归档根 ＋ 一张清单），不留在项目旁边。
4. **能跑的代码在真身，过程与结论在工作区的 `memory/`** —— 项目 README 只放指针。
5. **可见性建卡时就要定，默认"仅本机"**；外发要过敏感串扫描，公开要用户点头。
6. **改名要四处一起改**（真身目录、技能/包的 id、远端仓库名、卡目录名）。
7. **"我仓库里有"不等于能直接推** —— 先列远端仓库确认真名，别凭记忆新建一个同名的。
8. 判断不清时选**保守**：先不建、先不外发、先进 `scratch/`。撤回一个动作很容易，撤回一次披露不可能。

## 一、为什么非要"一处真身"（这是踩出来的）

同一份东西存在多处，几乎必然长出这三种病：

| 病 | 长什么样 | 后果 |
| --- | --- | --- |
| **同一份存三处** | 真身、工作区镜像、备份各一份 | 改一处忘两处；后来的人读到两份都能跑，**不知道哪份算数** |
| **映射不全** | 有的有镜像没真身、有的有真身没镜像 | 半年后自己也说不清"哪个是活的" |
| **各自演化** | 镜像被就地改过几行、真身也改了 | 两份都像真的，合并时才发现分叉 |

**药只有一味**：**一处真身**（唯一可写的地方）＋ **一张卡**（只登记、不复制）＋ **明确的退役去向**。
反过来，任何"为了同步而同步"的机制（定期镜像、双向同步器）都会变成第四个漂移源 ——
真身唯一之后，**这类机制应当退役**，而不是继续跑着互相追。

判断一个机制该不该留，只问一句：**"如果它停了，我会丢失什么？"** 答"什么也不丢"就是该停的。

## 二、三种存放形态（先选形态，再谈内容）

| 形态 | 真身在哪 | 工作区里放什么 | 什么时候用 |
| --- | --- | --- | --- |
| **内嵌** | `<工作区>/projects/<名>/` | 项目本体 | 工作区就是项目的家；单人单机的小件 |
| **外置＋卡** | 工作区**外**一个专门的根（自己挑，如主目录下的 `~/project/`；换个系统就是换个目录） | 一张 ≤40 行的登记卡 | 项目多；要跨会话/跨工作区复用；要给 agent 当技能 |
| **回退副本** | 归档根（如 `~/backup/files/`） | 卡改成指向归档路径并标 `archived` | 已退役、老版本、事故物证 |

选择顺序（照这个问自己）：

1. **以后还会改它吗？** 不会 → **别建项目**，放 `scratch/`（一次性产物）或 `handbook/`（可照做的流程）。
2. **会跨会话、跨工作区复用吗？** 会 → **外置＋卡**（真身是长期资产，值得有自己的 git）。
3. **只是本工作区的一次性产物？** → 内嵌，或干脆留在 `scratch/`。

> **真身根放在哪由你定**：重要的是"**只有一处**"。两种系统上的样子不一样（有人是主目录下的一个专门目录，
> 有人是某个盘里的一个文件夹），配置里写它的**绝对路径**即可 —— 脚本按你填的走，不假设任何固定位置。
>
> **"先小样后建项目"**：新东西先放 `scratch/<种类>/` 跑通**最小闭环**（真数据、真通路、一两条端到端），
> **用户确认**要长期维护，才升级成项目。理由很实在：**建项目要写 README、要 git、要维护卡**，
> 而大多数"可能可复用"的产物其实只跑一次。

## 三、建一个项目（四步，建议照做）

1. **小样先跑通**（在 `scratch/`），并让用户确认"要长期维护"。
2. **真身着地**：一个目录 ＋ `README.md`（是什么／怎么跑／依赖什么／当前状态／最后验证日期）
   ＋ `git init` ＋ `.gitignore`（把虚拟环境、构建产物、缓存、日志、**凭据**挡在外面）。
   **`git init` 只是本机建库，不等于外发** —— 保密的东西更需要 git，改错能回退。
3. **定可见性**（见第五节），然后按形态登记：`card` 形态写登记卡（照 `templates/projects/card.md`）。
4. **让台账跟上**：跑 `memory_query.py --rebuild --refresh`，条目进 JSON 台账与各区活窗口。

## 四、登记卡写什么（卡的全部价值在"真身"那一行）

| 项 | 说明 |
| --- | --- |
| **真身** | **本机实际的绝对路径**（照你系统上的写法写就行，两种系统写法不同，脚本都认），且真的存在 —— 体检 `cards` 项就靠这一行核对 |
| **可见性** | 仅本机／私有远端／公开远端；**建卡时就定**，默认"仅本机" |
| **类别** | `项目`（要长期演进）／`工具`（在用的小件）／`技能`（给 agent 加载的能力）—— 三种，别发明第四种 |
| **状态** | `open` / `absorbed` / `archived` / `dropped`；吸收后补「已吸收：<去向>」 |
| **git** | 有无本地仓库；有远端就写 `<托管方>/<仓库名>`（分支） |
| **指针** | 真身 README、相关记忆（相对链接） |

**卡里不写**：怎么跑的步骤（那在真身 README）、最近的改动（那在 `git log`）、任何密钥。
卡一旦开始"什么都写"，它就会变成第二个需要同步的副本 —— 又回到第一种病。

## 五、可见性：三级与推送闸门（安全默认）

| 级别 | 含义 | 建之前要做什么 |
| --- | --- | --- |
| **仅本机**（默认） | 没有远端 | 什么都不用做；`git init` 照建 |
| **私有远端** | 只有自己能看到 | 先扫敏感串；**默认建 private** |
| **公开远端** | 全世界可见，且**不可逆** | 用户**明确同意** ＋ 扫敏感串（含**历史**）＋ 确认没有密钥/内网地址/隐私 |

闸门要点（细节见 [隐私与密钥](隐私与密钥.md)）：

- **推之前必须扫，而且不只扫当前文件**：历史里的一次误提交，之后删掉也还在 `git log -p` 里。
  所以扫描要覆盖**将推送的那段历史**（逐提交看一遍），不看历史等于没扫。
- **挂了钩子也只是提醒**：钩子是"防手滑"，不是"保证"，绕过它只要一个环境变量；
  真正的保证是**你在推之前看过扫描结果**。
- **公开是不可逆的**：仓库一旦公开，可能已被抓取、镜像、进搜索引擎 ——
  删仓库、改历史都救不回来。所以"公开"这一级永远要人点头，不能由脚本默认。
- 反过来也别过度紧张：**真正的泄露路径通常不是 git**，而是"把秘密贴给了不该给的模型/服务"，
  以及"密钥写进了脚本、日志、命令参数"。分级要按"这东西泄露了会怎样"来定，不是按"听起来重不重要"。

## 六、命名（改一次名字要动四处）

- 规则：**项目名不带日期**（记忆与交流才按时间）；名字一旦定了**别改**，改名要同步所有引用。
- **改名的四处**：① 真身目录名；② 技能/包的 id（技能的 id 来自它的元数据 `name` 字段，
  **不是目录名**）；③ 远端仓库名；④ 工作区里的卡目录名。漏一处就留下一条断链或一个"半个名字"。
- **技能类仓库建议带后缀**（`-skill`／`-skills`）：和普通项目一眼区分。
- 名字撞车时（比如包名被别人占用），**统一改到底**，别只改一处留两套叫法。

## 七、和"已有远端仓库"打交道（迭代 ≠ 另起一个）

常见情形：用户说"这个我仓库里有"。**先查清楚，再动手**：

1. 列一遍远端仓库（有命令行工具就用它，或者直接看托管方的网页），**确认真名** ——
   记忆里的名字常常和实际不一致（踩过：以为叫 A，真名是 B）。
2. 如果是**同一个项目的新版本**：把新版本**接在旧历史上**（旧提交作为父提交保留），
   这样是普通 push、**不需要强推、也不丢旧版本**；旧版本随时能翻出来对比。
3. **不要**另建一个同名（或近似名）的仓库当"新版本" —— 那等于把同一个项目的历史割成两半，
   以后没人知道该往哪边提交。
4. 如果新旧确实无关（不同项目），才新建；新建时按第五节定可见性。

## 八、退役（别让它安静地消失）

- 真身**归档到回退副本根**，并在归档清单里写清：来源、日期、为什么退役、树的指纹（可选）。
- **卡留着**：把真身的路径改成归档路径，状态标 `archived`。
  删掉代码却留下卡，以后才有人知道"它存在过、在哪"；连卡一起删，就等于没做过。
- **跟着退役的还有它的自动化**（定时同步、镜像脚本、钩子）—— 一并挪进归档，
  否则它们会继续对着一个不存在的路径报错，或者更糟：悄悄重建一个空壳。
- 退役≠删除。真要删，先 `mv` 进工作区的 `trash/`（口径：**`mv` 不 `rm`**），过一阵再清。

## 九、常见漂移与对策

| 症状 | 对策 |
| --- | --- |
| 卡里的真身路径指不到（真身搬了） | 搬的时候就改卡；体检 `--only cards` 会提醒 |
| 真身有、卡没有（偷偷建的项目） | 要么补卡，要么确认它不归这个工作区管（体检会列出来） |
| 卡越写越长，快成第二份 README | 卡只留指针，说明挪回真身 README（体检按行数提醒） |
| 同一个项目两处都在改 | 定一处真身为可写，另一处只读或退役 |
| 想外发时才想起"里面好像有密钥" | 把扫描提前到**提交前**，而不是推送前 |
| 项目多到记不清哪个是活的 | 看工作区 `projects/README.md` 的活窗口；卡里的状态字段维护起来 |

## 十、这一篇的边界

- 它**只给建议**：不代替用户做决定，也不自动执行任何外发/删除。
- 体检的 `cards` 项**只核对形式**（卡在不在、真身指不指得到、字段有没有、卡长不长），
  **不评价内容好坏**，也不判断"该不该建"。
- 真身目录**在工作区之外**时，体检只读它、不改它；探不到就如实说一句，不猜数字。
