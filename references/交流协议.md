# 多智能体交流协议（exchange）

## 一、为什么有这套协议

不是防着谁，是为了两件具体的事：

1. **并发写入不打架**：两个智能体同时改同一个文件，会互相覆盖，复盘时看不出谁改了哪一行。
2. **结论需要归因**：答复里的数字**不自动成为结论** —— 出题方独立复核过，才算数。

所以分工的目标是"写入范围可查、复盘有据"，而不是"不信任对方"。

## 二、目录与角色

```
exchange/YYYY-MM-DD-主题/
├── task.md      # 测试文档：出题方写（自包含、可复现、含验收标准）
├── answer.md    # 答复文档：建目录时为空，只有作答方写
└── (可选) 附件：题目需要的输入文件、脚本、原始产物
```

| 角色 | 可以写 | 不要写 |
| --- | --- | --- |
| **出题方** | `task.md`、附件、全部记忆（`memory/`、索引、`handbook/`） | 测试进行中不动 `answer.md` |
| **作答方** | **只有 `answer.md`** | 不改 `task.md`、不写记忆、不动其它文件 |

同类测试在**同一目录内追加** `task-2.md` / `answer-2.md`，不要一天建一堆目录。

## 三、出题方清单

- [ ] `task.md` 写清：目标、输入与位置、可用的命令、**验收标准（怎么判定对错）**、
      代价上限（时间 / 调用次数）、交付物格式；
- [ ] 建一个**空的** `answer.md`（可放标题 + "（待作答）"占位）；
- [ ] **测试期间冻结被测对象**：正在被测的代码/文档不要一边测一边改 —— 否则答复对应的版本就说不清了。
      必须改时：要么重跑测试，要么让作答方在 `answer.md` 里钉住关键文件的 `sha256`，复核按**那个版本**判定；
- [ ] 把 task 与"只写 answer.md"这条约束**一起**交给作答方（原样转发脚手架打印的提示）；
- [ ] 用 Agent Teams 时，`team_task_create` 的 `write_scopes` 写 `exchange/.../answer.md`。

## 四、作答方要求

- 只写 `answer.md`；写清**结论 → 依据（命令 + 原始输出片段）→ 不确定的点 / 建议的下一步**。
- **不许猜**：数不出来就说卡在哪；题目不自包含就写明卡点后停下，不要反问式地改题。
- 鼓励写出"我不确定的点"和"建议的下一步"—— 这不是越界，能让复核更有价值。

## 五、复核（出题方做，也最容易被跳过）

**先定复核的取舍**：

- **小而短、质量高的步骤**（复跑基准、比对原始输出、重算 sha256）→ **自己重复一遍**；
- **长而繁琐、质量低的步骤**（重跑一轮耗时数分钟的付费模型调用）→ 不必重复，
  改为检查中间产物与依据是否自洽。

**复核结论必须说明验到哪一层**：

| 层 | 手段 | 能证明什么 |
| --- | --- | --- |
| 逻辑层 | 行数对得上、关系约束成立、总量守恒 | 内部自洽 |
| 文件层 | `sha256sum -c` | 字节一致 |
| **设备层** | `dd iflag=direct`（O_DIRECT 绕过页缓存） | 真读到了介质，不是缓存 |
| 新鲜度层 | 对比上游发布时间 / 数据最大日期 | 数据是不是最新的 |

教训：`sha256` 只花 0.17 秒就"通过"，其实读的是页缓存 —— **那不算验证**。

## 六、状态机

`task.md` 顶部一行，出题方维护：

```
状态: pending | answered | verified | absorbed | abandoned
```

| 状态 | 含义 | 谁推进 |
| --- | --- | --- |
| `pending` | 已出题，待作答 | 出题方 → 作答方 |
| `answered` | 作答方已交 | 出题方复核 |
| `verified` | 出题方独立复核过（写明验到哪一层） | 出题方写记忆 |
| `absorbed` | 结论已写进 `memory/` 或 `handbook/`（写明去哪了） | 完 |
| `abandoned` | 放弃（**必须写原因**） | 完 |

体检会提醒：`pending` 超过 `pending_max_age_days`（默认 3 天）就催办或标 `abandoned`。

## 七、测试 ≠ 可用产物

交流区只存**测试过程与答复**。测试里产出的可复用成果要搬走：

| 产出 | 去哪 |
| --- | --- |
| 定型的流程 / 结论 / 参数表 | `handbook/` |
| 可复跑的脚本、基准、产物 | `scratch/<种类>/` |
| 需要长期留的数据快照 | `archive/<种类>/<日期>/` |
| 只是这次回答的证据 | 留在 `answer.md`，不动 |

搬走后把状态改成 `absorbed` 并写明结论去向。

## 八、什么值得出题

- **口径类**：同一个问题换个入口/参数，结果是否一致（最适合交叉验证）。
- **可判定类**：有几个明确的、可独立算出的事实（数字、条目、行数）。
- **边界类**：库/盘/文件缺失时会不会静默给错答案。
- **回归类**：上次踩过的坑，再问一次看是否复现。

出题本身也是制度的一部分：**测试是验证"别人能不能只看文件就照做"**，
所以题目要当"给陌生人的说明书"来写。
